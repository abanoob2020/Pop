# قرارات معمارية مؤجّلة — XCAMP GYM

توثيق للبنود التي تتطلّب قرارًا معماريًا كبيرًا أو إعادة هيكلة، **لم تُنفَّذ** في مهمة
التحصين الأمني (التي التزمت: بلا rewrite، بلا تغيير schema/business logic، بلا كسر
وظائف). كل بند هنا مقصود صراحةً كعمل مستقبلي.

## 1. تعدّد المستأجرين (Multi-tenancy)
- **الوضع الحالي:** قاعدة واحدة `xcamp_gym` لمنشأة واحدة.
- **مستقبلًا (لو صار SaaS لأندية متعددة):** إمّا قاعدة/سكيمة لكل نادٍ، أو عمود
  `tenant_id` على كل جدول مع نطاق إجباري في كل استعلام. الأخير يتطلّب طبقة وصول بيانات
  موحّدة تفرض النطاق تلقائيًا (تفادي التسريب بين المستأجرين).
- **الأثر:** إعادة تصميم schema + كل الاستعلامات. قرار كبير — خارج نطاق التحصين.

## 2. Framework (Laravel/Symfony)
- **الوضع الحالي:** Raw PHP بمصادقة/جلسة/CSRF يدوية (تعمل وآمنة، لكنها إعادة اختراع).
- **مستقبلًا:** الانتقال يمنح ORM، migrations، middleware للتفويض، حماية CSRF مدمجة،
  وحاوية اعتمادات. **لا يُنفَّذ الآن** (المهمة تمنع rewrite).

## 3. نظام Migrations بإصدارات
- **الوضع الحالي:** ملفات SQL مرقّمة إضافية (`08…20`) بلا جدول إصدارات ولا rollback.
- **مستقبلًا:** أداة migrations (Phinx أو ما يكافئها) بجدول `schema_migrations`
  و up/down. يحسّن التتبّع والتراجع مع نمو المخطط.

## 4. تضييق CSP (حذف `'unsafe-inline'`)
- **الوضع الحالي:** CSP بأصول ذاتية «آمنة مبدئيًا» تُبقي `'unsafe-inline'` (ضروري: ~20
  معالج inline + أنماط inline + كتلتا `<script>`) وبلا `'unsafe-eval'`. أداة قياس
  Report-Only متاحة (`CSP_REPORT_ONLY=1` + `csp_report.php`).
- **الخطة التفصيلية والمراحل:** انظر [`docs/csp-plan.md`](docs/csp-plan.md) — Stage 2 (nonces
  للسكربت)، Stage 3 (ترحيل المعالجات إلى `addEventListener`)، Stage 4 (حذف `'unsafe-inline'`
  من `script-src` والفرض). كل مرحلة تمرّ بـ Report-Only + اختبار كل الصفحات قبل الفرض.

## 5. Rate-limiter مركزي (DB/Redis)
- **الوضع الحالي:** تقييد محاولات الدخول بتخزين ملفّي (`sys_get_temp_dir`) — best-effort،
  محدود التزامن، وغير مشترك بين عدّة خوادم.
- **مستقبلًا:** limiter مدعوم Redis/DB (عدّادات ذرّية + TTL) يعمل عبر عدّة نسخ تطبيق،
  ويغطّي نقاطًا أكثر من الدخول (إعادة تعيين كلمة المرور، نقاط AJAX الحسّاسة).

## 6. طبقة API + تطبيق موبايل
- **الوضع الحالي:** صفحات PHP مُخدَّمة خادِميًا، بلا طبقة API.
- **مستقبلًا:** REST/JSON API بمصادقة رموز (JWT/opaque) لدعم تطبيق موبايل — يتطلّب تصميم
  مصادقة/تفويض منفصلًا عن جلسات الكوكيز.

## 7. إعادة تعيين كلمة المرور والتحقّق
- **الوضع الحالي:** تعيين/تغيير كلمة مرور العضو عبر الطاقم؛ لا تدفّق «نسيت كلمة المرور»
  ذاتي الخدمة برموز موقّتة.
- **مستقبلًا:** تدفّق reset برموز مُوقّعة قصيرة العمر عبر البريد/الرسائل (مرتبط ببوّابة
  الإشعارات المقترحة).
